Release 3.5.0

Magnets that actually work

A magnet link is four lines of text that promises a file you cannot see yet. For a long time, Footorrent treated that promise as enough: it announced, connected, and started writing before it really knew what it was downloading. If anything on the wire went sideways, the window just said “fetching metadata” until you gave up.

2026-11-09 · dach-a · Rust, no runtime · ~3 MB binary

Metadata first, disk second

Adding a magnet is now two deliberate steps. The first contacts the swarm, fetches the info dictionary over BEP 9/10, hashes it against the magnet's info hash, and reports the real name, exact byte size, piece count and file list. Nothing is created on disk. Only then does the window ask where the download should go and start it.

That sounds like polish. It is really a correctness change: the size you approve is the size you get, and a link that cannot produce verified metadata fails while the dialog is still open, instead of leaving a half-named folder behind.

Three bugs that made magnets look broken

Most of this release was diagnosis. Each bug below was invisible from the outside — the client looked busy, and every magnet “just failed”.

1. The extension id was somebody else's

BEP 10 has each side advertise the id the other must use. Our requests went out under the peer's id (often 3), but replies come back under our advertised id (1). The receive loop matched the wrong number and discarded every real metadata reply. Peers were healthy; we were reading the wrong mailbox.

2. Routine chatter was treated as rejection

A peer that sent a bitfield or an unchoke before its extension handshake was counted as not supporting ut_metadata. Ordinary clients do this constantly, so magnets failed against perfectly good peers. Both the metadata and download loops now ignore that chatter, and our handshake sets the extension bit so peers actually answer.

3. The peers we found were thrown away

The worst one. Resolving a magnet discovered 211 peers — and then /api/start dropped them, re-announced to the magnet's own tracker list, and waited. When that list was dead, the job sat at zero peers and zero bytes forever. The peers from resolve are now handed straight to the session that starts the download.

When the announce list is dead

Old magnets carry tracker lists that rot: one returns 403, one is a UDP host that never answers, one is an I2P name that will not resolve. Asking them in sequence let the first failure eat the whole budget, so later trackers never got a turn.

  • Announces now go out in parallel — 8 s each, 20 s overall.
  • If the whole list yields nothing, well-known public trackers are tried before the DHT.
  • The DHT gets a second hunt if its first answer is thin, and metadata exchanges run in parallel batches of eight in shuffled order.
  • Failures say how many peers were tried and what the last one said, instead of one misleading tracker error.

The result is visible in the window: the confirmation step says when a magnet's own announce list did not answer and public trackers were used, every peer row shows its live rate, and a failed resolve keeps the links in place behind a Retry button.

Measured, not asserted. A Sintel magnet carrying a deliberately dead announce list (403 + two silent UDP trackers + an unresolvable I2P host) resolved in 17–42 s, reporting 129,302,391 bytes, 987 pieces, 11 files and 207–211 peers. Starting it wrote 917,504 bytes in the first minute at 15–26 KB/s across 6 peers.

What this release does not fix

A dead swarm is still dead. If every peer in the DHT and every tracker refuses the connection, the client cannot invent a source — it can only be honest about it. That is the point of the new error text: “tried 27 of 27 peer(s): connection refused” tells you the swarm is gone, not that the client is confused.

One magnet from a report is still unresolved for a simpler reason: its hash arrived truncated, so there was nothing to query. If you hit a failure, paste the full 40-character info hash and the tracker list — that is enough to tell a dead swarm apart from a client bug.

Upgrade

Prebuilt binaries for macOS, Linux and Windows are on the releases page; the CLI, web UI and macOS window all come from the same Footorrent binary. The full list of changes is in the changelog.

Commits behind this post: 2fc6640 (parallel announces, public fallback, batched metadata), 46edeb8 (hand resolved peers to the download) and 9f4197c (tracker fallback, per-peer rates, retry).
