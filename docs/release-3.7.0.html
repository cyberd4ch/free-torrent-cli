Release 3.7.0

One app, two architectures, and a pause key

3.6.0 made the client honest about what it was doing. This one is about the machines it runs on: a macOS app that opens on an Intel Mac as readily as on Apple silicon, Linux arm64 archives that finally exist, a terminal that can pause instead of just watching, and CI that installs the result rather than trusting it.

2026-11-10 · dach-a · Rust, no runtime · ~3 MB binary

What changed

A universal macOS app

The window shipped as an arm64 bundle, which meant an Intel Mac installed a Footorrent.app that could not start. The release job now builds both architectures of the engine and compiles the Swift window twice, then lipos each pair into one file — so the zip contains a single app with x86_64 and arm64 slices, not two zips anyone has to choose between.

install.sh stopped guessing. It reads the architectures out of the bundle it just unpacked and keeps the app only if the machine has a slice; otherwise it writes the browser launcher and says so. Pinning an older release on an Intel Mac therefore degrades to a working window in the browser, not a silent failure.

Linux arm64

ftc-linux-arm64.tar.gz is built on an arm64 runner against aarch64-unknown-linux-gnu and joins the release matrix, so the installer no longer has to answer Linux/aarch64 with "no build yet". The archive is an ordinary ELF aarch64 binary with the footorrent alias beside it, exactly like the x86_64 one.

Older releases do not have that asset. Rather than dying on a 404, the installer prints one line saying the release has no arm64 archive and how to build one.

Pause, from the terminal

The engine has had a pause gate since the window got a Pause button; the CLI simply never used it. Now p and Enter flips it. Workers park between blocks, the bar turns amber, and the stats say how much has actually landed:

‖ ███████████▏░░░░░░░░░░░░░░░░░░ · paused · 768 KB / 2.0 MB

That frame is from a real run: a 2 MB torrent served by a local peer, paused a third of the way in, resumed with the same keys, finished. The file that landed hashes identical to the source and no piece was fetched twice. The listener reads whole lines on purpose — raw mode would mean termios and a dependency — and it only exists when stdin and stdout are both terminals, so a piped run never blocks waiting for input.

The installer is tested, not assumed

Every push now runs install-smoke on x86_64 and arm64: it builds a real archive, hashes it, points install.sh at it with FTC_BASE_URL, and checks that the right asset was chosen, the digest says sha256 ok, the binary is executable, the alias is a symlink and the architecture matches. Three negative paths are checked in the same job: the opt-out prints sha256 SKIPPED — FTC_NO_VERIFY is set, a release without checksums says sha256 SKIPPED — this release carries no SHA256SUMS, and an unsupported machine is refused by name rather than by a curl error.

Measured, not asserted. Paused at 768 KB of 2.0 MB and resumed to completion: the output file's SHA-1 matched the source exactly. The smoke job installs on both architectures and prints Footorrent 3.7.0 (ftc) from the installed binary, not from the build tree.

What 3.7.0 does not fix

The macOS bundle is still ad-hoc signed (codesign --sign -), so a download straight from the browser meets Gatekeeper. A Developer ID and notarization are the fix, and they need an account this project does not have yet.

Pause is line-based: press p, then Enter. Catching a single keypress would need termios and a dependency; the engine parks between blocks, so one line of latency changes nothing.

A Windows window is still the missing front end — the engine, the CLI and the web UI all run there today.

Upgrade

Prebuilt binaries for macOS (universal app and per-arch archives), Linux (x86_64 and arm64) and Windows are on the releases page under v3.7.0. The authoritative list of changes is in the changelog.
